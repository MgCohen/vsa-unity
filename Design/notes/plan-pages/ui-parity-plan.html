UI Parity Plan

Two design systems with the same component IDs. Screens move from HTML to Unity as JSON, and the JSON names components, not pixels.

TARGET PHASE 1 NEXT

HTML and Unity each have a design system: tokens, components and a gallery. A shared component ID (for example ds-button) connects the two implementations.

A screen exists one time, in HTML. A parser writes it as screen.json. A Unity builder and an HTML preview make the screen from that JSON.

Source of truth rules
  • Values: tokens.css. Unity never has its own value for a token.
  • Component look: the HTML component is the reference. The Unity component follows it, and the parity test measures the difference.
  • Component behavior that HTML cannot show (sound, haptics, animation curves): Unity only.
  • Screen layout: screen.html. The Unity screen prefab is output. Do not edit it by hand.
  • Game logic: neither. Presenters attach to node IDs in the screen prefab.

Component parity test

Sprites that come from tokens (for example the button face) also need an export again. Phase 2 decides which values are sprites and which are live (see Questions).

Flow: change a component · a person on the Unity side
  1. Change the component CSS. The HTML gallery shows the result.
  2. Run the component parity test. It fails for that component.
  3. Change the Unity component until the test passes.
  4. All screens that use the component update on both sides. No screen parse is necessary.

Rules for the parser in phase 1
  • A node is an element with an id. Other elements are ignored, but their children are examined.
  • A ds-* class makes a component node. The parser does not examine its inside.
  • Absolute positions only. If a node uses flex or grid layout, the parser stops with an error.
  • Units are CSS px = canvas units, for a 1920 × 1080 reference size.
  • The parser never reads colors, fonts or shadows.

Working rules for all phases
  • Zero install: Unity needs only the Editor. Tools use what this computer has (Edge, Node, PowerShell).
  • Build on a seen need: no helper or framework before a step needs it.
  • Each phase starts only after the earlier phase passes.
  • Send screenshots, the interactive HTML and a Unity touch video for each result.
  • Keep the Unity Editor open across the spikes.
Q1 · Where do anchors come from? PHASE 1
OptionForAgainst
A. From the computed style (right + bottom set → anchor 1,0)The designer writes normal CSSSome CSS has no clear anchor (centered with transform)
B. A data-anchor attributeExact, simple parserExtra work, and it can disagree with the CSS

Recommendation: A, and the parser stops on a case that it cannot read. Add B only for those cases.

Q2 · What is the component ID? PHASE 1
OptionForAgainst
A. The block class (ds-button)Already in the HTML, no duplicateA style class also carries meaning
B. A data-component attributeClear meaningTwo names for one thing

Recommendation: A. Each ds-* block class is a component ID.

Q3 · Can a person edit the generated Unity screen? PHASE 1
OptionForAgainst
A. No. The prefab is output, the builder replaces it.The HTML stays the source of truthUnity-only additions need another place
B. Yes, with a merge on each buildFlexibleHard merge rules, screens drift

Recommendation: A. Game code and Unity-only parts attach by node ID, outside the generated prefab (for example a prefab variant).

Q4 · Which values are sprites and which are live? PHASE 2

Phase 0 baked the button face into sprites. A token change then needs an export again.

OptionForAgainst
A. Sprites from HTML for each stateExact lookExport on each token change
B. Unity draws from tokens (colors, radius, text)Live token changeGradients and shadows need a shader or a mesh

Recommendation: decide in phase 2. Probably B for colors and text, A for complex art.

Q5 · Flex layout: LayoutGroup or fixed positions? PHASE 4

Recommendation: phase 1 supports only absolute positions. Phase 4 maps flex rows and columns to HorizontalLayoutGroup and VerticalLayoutGroup, so lists can grow at runtime.
