Open generics in Umpire

Umpire uses open generic classes for handlers, hooks, validators and services. It does not register open presenters. Microsoft DI and the Unity linker limit them. This page lists the limits, the use cases, the tested cases, the current solution, five other solutions and the requirements for a final solution.

Why open generics

One generic class serves a family of types, so the app has no copy for each type. Game code often uses structs for these types, for example Health and Score.

UseExampleBase with [AutoRegister]
A command for each resourceChangeResourceHandler<T> for Health, ManaCommandHandler<,>
A request for each typeGetHandler<T>RequestHandler<,>
An event for each typeChangedHandler<T> for Changed<T>IntegrationEventHandler<>
A rule for each typeDamageRule<T> for Sword, DaggerAn app interface
A validator for each typeRangeValidator<T>Validator<>
A plain service for each typeStore<T>[AutoRegister] on the class

The pipeline does not resolve handlers, hooks, validators or presenters as DI lists. It indexes the closed types from AppTypes.Implementations(), and it creates each one with ActivatorUtilities.GetServiceOrCreateInstance(scope, closedType) (vsa-template 88de76b, PipelineRun.cs:94, Pipeline.cs). Umpire uses DI lists only for non-generic services (Operation, IIntegrationEventObserver). So the list cases in Problems apply only to app code that resolves IEnumerable<ISomething<T>>.

Requirements (draft)

These requirements define a valid final solution. The stripping, list and NativeAOT rows are decided. The other rows are a draft.

Must

  • The same app code works in the Editor, on IL2CPP and on .NET.
  • Umpire bases work over structs and classes.
  • A failure shows in the Editor, not only in a build.
  • Works at stripping Minimal.
  • A single resolve and a list resolve work for each registered service.
  • A list resolve gives each item one time, with the same result on all platforms.
  • IServiceCollection stays the composition API.

Should

  • No marker for types that code names.
  • Two or more type parameters.
  • Only used combinations are registered.
  • No link.xml for consumer code.

Acceptable limits

  • A type that only reflection makes needs a marker, if the error names the missing marker.
  • A consumer open registration over a struct fails on IL2CPP, if a check shows it in the Editor.
  • Stripping Medium and High are not supported.

Non-goals

  • No .NET NativeAOT support. Reason: no user needs it now.

Open questions

  • Are the draft rows correct: no marker, two type parameters, used combinations, no link.xml?
  • Is stripping Low a requirement?
  • Does Unity run a Roslyn generator for code in Assets/ and in asmdefs?
  • Is a generic class with two type parameters necessary?
  • Is solution A useful as a fallback to B for message dispatch?

L1 · DI maps one open shape only

A DI open registration maps a service to an implementation with the same type parameters, in the same order. Umpire bases put the type parameter inside another type, so DI cannot register them open on any platform.

services.AddSingleton(typeof(IStore<>), typeof(Store<>));      // works: same parameters

public sealed class ChangedHandler<T> : IHandler<Changed<T>> { }
services.AddSingleton(typeof(IHandler<>), typeof(ChangedHandler<>));
// wrong: this maps IHandler<T>, not IHandler<Changed<T>>

L2 · DI refuses open registrations closed over a struct

If RuntimeFeature.IsDynamicCodeSupported is false, DI refuses to close an open registration over a struct. IL2CPP reports false. The guard examines only the direct type arguments.

// Microsoft DI 8.0, CallSiteFactory (simplified)
if (VerifyAotCompatibility && argument.IsValueType)
    throw new InvalidOperationException("Unable to create a generic service for type ... because ... is a ValueType.");
  • The Unity runtime can do the work: MakeGenericType over a struct that no code names works on IL2CPP (case R1). So the limit is the DI guard, not the runtime.
  • No switch stops the guard. The netstandard2.0 DI build has no guard, but it breaks scoped resolves on IL2CPP (solution D).

L3 · Stripping removes code that only reflection uses

What the cases show

  • An undeclared type (U6, U10) fails the same way on all platforms. This is the cost of the marker.
  • IL2CPP adds failures only where an open registration closes over a struct (D2, D3, D6, D9, U7).
  • An open registration next to a closed one gives duplicates on all platforms (D6, D7, U7).
  • A consumer open registration hides a missing marker for classes only (U8). For structs it fails on IL2CPP only.
  • VContainer has no struct guard (V2), but its lists skip open registrations (V6, V8). A single resolve and a list resolve then disagree.
  • VContainer does not match nested shapes. It returns a wrong instance with no error (V9).

Use cases

The Umpire compose meets 10 of 11 use cases on Mono and IL2CPP, and gives a duplicate in the list of Edge. Microsoft DI meets 2 and VContainer meets 4, with open registrations. Each nested shape (IHandler<Put<T>>) and each non-generic list of open classes fails in both containers.

Each case has a theme from a card game, and a generic version in neutral types. The spike runs the generic version. "Microsoft DI" and "VContainer" are plain containers with an open registration: the container closes the type. "Umpire compose" is the scan: Umpire closes the type and registers closed types in Microsoft DI. The players use stripping Minimal. Results: Probe/Results/player-*-Minimal-OptimizeSpeed.log, checks spike:*. R1 to R4 are real cases, T1 to T5 are invented cases, and N1 is a case that the review found. At start, the Umpire scan closes each open [AutoRegister] class over each fitting [TypeArgument] type. It registers only closed types.

Technology

  • VContainer 1.19.0 from its Git URL, the same version as the vsa-unity manifest.
  • VContainer reads RuntimeFeature nowhere, so it has no struct guard. It closes types with MakeGenericType (R1 shows that IL2CPP supports this).
  • Autofac and DryIoc map nested open generics, from their documents. They are not tested.
